# 从传统数据工程到 AI 数据工程

这个项目面向已经工作的传统数据工程师，而不是为学生重新编排一套计算机课程。典型参与者可能长期负责
SQL、ETL、数仓建模、指标加工和调度运维；也可能已经在日常工作中使用 LLM、开发 Agent 或接入 AI 应用，
但仍不知道一条数据如何进入训练、如何影响模型，以及规模化训练为什么会被计算和存储限制。

职业困境不在于 SQL 突然失去价值，而在于只交付 SQL 结果已经不足以形成新的稀缺性。真正的转型不是抛弃数据工程，
而是把已有能力连接到模型训练目标，从“表、任务和报表交付”向“数据版本、训练供给和模型反馈”推进。

## 三类核心参与者

### SQL/数据开发型

擅长取数、加工和调度，但主要价值仍体现为需求响应速度。转型重点是建立软件工程、数据契约、样本语义和实验意识，
让 SQL 成为构造 AI 数据资产的工具，而不是职业能力的上限。

### 数仓建模/数据平台型

熟悉分层、维度建模、质量、血缘和分布式计算。转型重点是把这些方法迁移到 Dataset、Token、Shard、Run 和模型版本，
并理解 DataLoader、Checkpoint 与训练并行带来的新约束。

### AI 应用/Agent 实践型

已经会调用模型、搭建 Workflow 或 Agent，但工作主要停留在推理应用层。转型重点是向下理解训练与评测数据：
模型能力来自什么数据、数据问题如何暴露、如何用系统化的数据工程持续改进模型。

## 责任对象发生了变化

传统数据工程常以表为交付对象：

```text
业务事件 → 清洗建模 → 指标表 → 报表或应用
```

AI 数据工程以可训练数据版本为交付对象：

```text
原始内容 → 质量与治理 → Token Sequence → 训练 → 评测 → 数据改进
```

第二条链路多了三个关键责任：样本语义、训练系统、模型反馈。

## Data + AI 不等于 Agent 开发

Agent 工程解决“如何让现有模型完成业务任务”，AI 数据工程解决“如何持续向模型和评测系统交付可靠数据”。
两者可以协作，但责任对象不同：

| 方向 | 主要对象 | 典型问题 |
| --- | --- | --- |
| AI 应用/Agent | Prompt、Tool、Workflow、Memory | 如何完成业务任务、提升调用成功率 |
| AI 数据工程 | Document、Sample、Dataset、Shard、Manifest | 数据是否可训练、可治理、可追溯 |
| AI Infra/训练系统 | GPU、通信、Checkpoint、Storage | 如何稳定、高效地完成训练和推理 |

本项目位于后两者的连接处。我们会把 LLM Judge 或 Agent 当作数据加工工具，但它们的输出同样必须被版本化、评测和追溯。

## 已有优势

数据工程师已经具备很多难以替代的基础：

- 能把复杂业务过程拆成稳定数据层；
- 理解分区、Shuffle、倾斜、批处理和容错；
- 重视血缘、口径、质量和可复现；
- 能建设长期运行而不是一次性 Notebook；
- 知道生产结论必须来自日志、产物和回读。

这些能力直接适用于大规模语料加工和训练数据平台。

## 必须补齐的部分

### 模型如何消费数据

需要理解 Token、Sequence、Mask、Batch 和 Loss，才能判断一次文本处理是否改变训练语义。

### 语义质量

空值、唯一键和 Schema 只能保证结构质量。训练数据还需要处理近似重复、知识密度、语言、领域、安全、许可和评测污染。

### 训练与 I/O

需要理解 DataLoader、GPU 等待、训练并行和 Checkpoint，才能把数据吞吐与训练成本联系起来。

### 实验闭环

不能只凭规则通过率宣布数据更好。必须固定训练条件，通过 Loss、能力评测和失败样例验证数据版本变化。

### 工程化代码

对只在 SQL 平台中工作的参与者，Python、测试、CLI、Git 和可复现环境也是转型的一部分。但项目不会单独开一门编程课，
而是在真实 Lab 中逐步补齐：先读懂和运行，再修改一个模块，最后独立完成实验。

## 推荐的 T 型能力

纵向深度选择“训练数据质量与数据资产”：

- 数据构造；
- 质量、去重和治理；
- Dataset Manifest 和血缘；
- 数据版本 A/B 与模型评测。

横向宽度覆盖：

- Tokenization 和训练基础；
- smallpond 等数据计算系统；
- 3FS 等 AI 存储系统；
- DataLoader、分布式训练和 Checkpoint。

不需要一开始同时成为算法研究员、CUDA 工程师和存储内核专家。先完成一条端到端链路，再根据真实瓶颈选择纵深。

## 最优学习方式：一个项目反复升级

项目不会让参与者在每个阶段更换一个互不相关的 Demo。所有 Lab 共同维护同一条数据—模型链路：

1. 先用很小的数据建立 Document → Token → Loss；
2. 加入数据污染和质量规则，完成第一次受控 A/B；
3. 增加数据规模，用 DuckDB 和 smallpond 观察 Partition、Shuffle 和失败；
4. 接入 DataLoader、Checkpoint 和 I/O Profile；
5. 用 3FS 理解 AI 存储的设计边界；
6. 回到正式数据版本 A/B，从模型失败归因到数据并发布毕业项目。

这种顺序避免两个常见误区：一是把 AI 数据工程学成新的名词表，二是研究了大量底层系统却从未证明它们解决了自己的问题。

## 与日常工作的连接

每个阶段都应选择一个现有工作概念做迁移，而不是假装脱离职业背景从零开始：

- 把一条 ODS → DWD → ADS 链路映射为 Raw → Normalized → Train Candidate → Shard；
- 把表级血缘扩展为 Source → Document → Sequence → Run → Metric；
- 把数据质量规则扩展为近似重复、评测污染和可训练性；
- 把任务 SLA 扩展为有效 Token 产出、DataLoader Wait 和恢复时间；
- 把数据版本发布扩展为 Dataset Manifest 与模型版本关联。

如果公司已有 RAG、Agent、模型评测或合成数据场景，可以使用脱敏、许可清晰的数据结构复刻问题，
但不能把公司数据、密钥或无法公开的运行证据提交到仓库。

## 职业成果应该长什么样

完成本项目后，最有价值的作品不是“读完了多少论文”，而是：

- 一个可复现的训练数据版本；
- 一份可以追到原始文档的 Manifest；
- 一条 smallpond 数据加工 Pipeline；
- 一次 DataLoader 或 Checkpoint 性能诊断；
- 一次固定预算的数据版本 A/B；
- 一篇明确区分本地、集群和生产证据的技术报告。

这些成果同时体现传统工程可靠性和 AI 时代的模型意识。

对外讲述时，重点不是“我学过 smallpond 和 3FS”，而是：

```text
我面对什么数据/训练问题
→ 如何定义数据契约和实验变量
→ 如何实现并测量
→ 结果如何影响模型或系统
→ 证据边界和下一步是什么
```

这套叙事可以用于面试和技术分享，更重要的是，它也能直接迁移到真实团队的数据平台与 AI 项目中。
